# v1.2 domain-correctness design

## Purpose

Version 1.2 turns the repository from a working demonstration with several incompatible analytical paths into one coherent public demonstration. It keeps the Home Credit dataset and the public FastAPI/Streamlit deployment, but removes claims that the data cannot support.

The accounting calculation takes priority over a convenient dashboard result: a score that cannot be connected to a valid loss calculation, a collectable input contract and a clearly bounded interpretation is not a credible credit-risk demonstration.

The revised release therefore accepts a narrower public form and a less flattering benchmark story in exchange for traceability: every live input exists in the fitted profile, every displayed loss follows one tested calculation path, and every report refers to the same persisted model bundle.

## Public model contract

The served model will be retrained as the `public_demo` profile. It will use only 15 inputs a dashboard visitor can provide: loan type, age, employment tenure, income, credit amount, annuity, goods price, car/property ownership, children, family members, education, income type, family status and occupation. `ORGANIZATION_TYPE`, `REGION_POPULATION_RELATIVE` and `OWN_CAR_AGE` leave the served profile because the existing form always omitted them even though the first two were complete in training data. Occupation remains optional because 31.15 per cent of the held-out data lacks it.

Amounts are described as dataset monetary units. They are not labelled rand because Home Credit's public competition table does not establish a South African currency scale.

The API rejects non-finite values, impossible age/employment combinations, a repayment greater than requested credit, unsupported categories and unknown fields. The dashboard derives occupation choices from the persisted model bundle rather than accepting arbitrary text.

## PD modelling and evaluation

The public-demo LightGBM model keeps the stratified 60/20/20 split with seed 42. Hyperparameters are selected with five-fold cross-validation on the training fold, early stopping uses validation, and the test fold remains untouched. The selected tree count is then refit on train plus validation before one final test evaluation. Artefact metadata records the profile, model parameters, selected tree count, data hash, package versions and test metrics.

An application-profile logistic regression is trained on the same 15 fields and evaluated on the same test fold. The report must show AUC, PR-AUC, Brier score and log loss for both models. The decision section must also show approval rate, default recall and declined-group precision at the economics-derived threshold. Calibration reporting includes Brier score, calibration intercept, calibration slope and a reliability plot evaluated on the untouched test set. Calibration is reported, not fitted, unless a validation-only calibration method demonstrably improves the selected metric.

## ECL demonstration

`src/ecl_core.py` becomes the single calculation path. For each month, marginal default probability equals survival to the start of the month multiplied by the conditional monthly default probability. Stage 1 uses a 12-month horizon; Stage 2 uses the remaining term; Stage 3 assumes an immediate credit-impaired cash shortfall and therefore applies the scenario LGD to EAD at the first discounted month. Scenario weights must sum to one.

The code uses a static EAD and scenario LGD, so each scenario loss is bounded by `LGD x EAD` and weighted ECL is bounded by the maximum scenario LGD times EAD. It is an IFRS 9 mechanics demonstration, not an accounting engine: it does not contain contractual cash-flow schedules, observed recoveries, local outcomes or real risk migration history.

`src/ecl.py` will generate a deterministic three-account mechanics report from this core instead of a synthetic portfolio summary that pretends two different models are origination and current PD. The report will use dataset monetary units and clearly state the illustrative inputs.

## Explainability and interface behaviour

Reason-code wording operates on business units, not transformed model values. `DAYS_BIRTH` is rendered as age in years, and `DAYS_EMPLOYED` as employment tenure in years. The reason-code panel separates risk-increasing factors from mitigating factors so a declined decision is not explained by a favourable SHAP contribution.

The dashboard uses the hosted API when available. Its local fallback remains clearly labelled and loads the same versioned bundle. A public score must never create missing values for a feature that is required by the public-demo profile.

## Artefacts, reports and security

Reports and figures that describe the former full-information model are removed from the current public report set. If retained for learning purposes, they live below `reports/archive/full_information_model/` and carry an opening statement that they do not describe the deployed service. No archived report may be linked from the README.

The README, model card, decision log and repository description will describe the deployed model as a public demonstration. The README will add the same-profile benchmark and operational test-set metrics, plus a direct statement that the project is not suitable for credit decisions or IFRS 9 provisioning.

Direct runtime dependencies will be upgraded to patched versions compatible with Python 3.12. `pip-audit` becomes a CI step for each requirements file. Dependabot covers the root, API and dashboard dependency locations, and security alerts are enabled through the repository settings when the authenticated GitHub account permits it.

## Testing and release gates

Tests are written before each behaviour change. Required regression tests cover survival-weighted ECL, ECL bounds, Stage 3 treatment, scenario weights, semantic age/employment explanations, public-model feature completeness, request plausibility checks and same-profile benchmarking. CI starts the built API image and makes a real prediction after the Docker build.

The release gate is: full test suite, Ruff lint/format, clean `pip-audit` output for root/API/dashboard requirements, API Docker smoke test, Docker Compose dashboard-to-API smoke test, live Render health/predict check and live Streamlit score check. A release may document an unresolved deployment credential block, but it may not claim a public deployment was verified without that check.
