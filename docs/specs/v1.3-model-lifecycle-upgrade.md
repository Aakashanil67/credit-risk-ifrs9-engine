# Model Lifecycle Upgrade Specification

## Purpose

The project already trains, evaluates, explains, serves, and documents a constrained public-demo
probability-of-default model. This release adds the evidence that is still missing from the model
lifecycle: uncertainty around reported metrics, controlled challenger experiments, drift and data
quality monitoring, an operational runbook, and privacy-safe service telemetry.

The work must strengthen the existing project without pretending that a historical Kaggle dataset
is a live lending portfolio. Every generated monitoring batch is a labelled replay or stress test,
not production data. Every threshold is illustrative until a lender calibrates it on its own data
and governance process.

## Outcomes

The completed release must provide:

1. Deterministic 95% bootstrap confidence intervals for AUC, Gini, KS, Brier score, PR-AUC, log
   loss, and material group differences.
2. A development-only challenger study comparing the current 15-field LightGBM model with:
   - sigmoid and isotonic probability calibration;
   - five ratios derived only from the existing public inputs;
   - calibrated versions of the derived-feature challenger.
3. Predeclared acceptance gates so the deployed model is not replaced merely because one metric
   moved in a favourable direction.
4. A serialisable monitoring reference containing aggregate distributions only—no applicant rows.
5. A batch monitor for schema quality, missingness, unseen categories, feature PSI, score PSI,
   approval-rate movement, and performance when outcomes are available.
6. A deterministic replay/stress demonstration with baseline, mild-shift, and severe-shift batches.
7. A validation report and monitoring runbook that state what is measured, what triggers review,
   and what the project cannot establish.
8. Structured API request logs containing operational metadata but no request payload, query string,
   applicant attributes, or client IP address.
9. A small repeatable load-test utility reporting success counts and latency percentiles.
10. Updated public documentation and architecture that distinguish service version, model version,
    offline validation, and simulated monitoring.

## Non-goals

- Do not claim production IFRS 9 compliance, lending suitability, South African applicability, or
  legal fairness.
- Do not introduce Kubernetes, Kafka, a feature store, Airflow, MLflow, Prometheus, or a database.
- Do not add bureau variables, gender, or non-collectable source fields to the served model.
- Do not create synthetic outcomes and describe them as realised defaults.
- Do not choose or promote a challenger using the existing test fold.
- Do not alter the public request schema in this release.
- Do not retrain or overwrite `models/public_demo/` unless a later, separately reviewed promotion
  plan is approved after the challenger report is generated.
- Do not log applicant payloads, SHAP values, decisions, reason codes, IP addresses, or query strings.
- Do not add a runtime dependency when NumPy, pandas, SciPy, scikit-learn, LightGBM, matplotlib,
  httpx, or the Python standard library already provides the required capability.

## Data protocol

- Preserve the existing deterministic 60/20/20 split with seed 42.
- Treat train plus validation as the development sample for cross-validated challenger work.
- Generate five-fold stratified out-of-fold predictions on development data. Each row must be
  scored by a model that was not fitted on that row.
- Evaluate sigmoid and isotonic calibration by cross-fitting over the out-of-fold development
  predictions: each calibrated row must also come from a calibrator that did not see that row's
  label. Fit a final calibrator on all out-of-fold development predictions only after evaluation,
  and only if a candidate passes the predeclared gates.
- The challenger report must not read or score the test fold. The current test results remain the
  versioned v1.2 reference; this avoids another round of model selection against the same holdout.
- Challenger selection remains development-only and completes before any monitoring demonstration
  uses the frozen test fold.
- After final model evaluation, split the 61,503-row frozen test fold deterministically and
  stratify by `TARGET` using seed 42. Allocate exactly 10,000 rows to the replay window and the
  remaining 51,503 rows to the monitoring-reference window.
- The two monitoring windows must be disjoint. Both are out of sample relative to the model fit.
  Use the reference window for feature, score, approval and performance baselines; use the replay
  window for baseline and stressed batches.
- This post-selection split is for monitoring demonstration only. It must not influence challenger
  selection, model promotion, threshold selection or the published incumbent test metrics.
- Bootstrap resampling must be stratified by target and deterministic with seed 42. Candidate-gate
  intervals use 1,000 fixed 20,000-row m-out-of-n resamples for feasible regeneration; their point
  estimates still use every development row. Published incumbent test intervals use full-size
  stratified resamples.
- Generated JSON references may contain bin edges, proportions, category labels, thresholds,
  aggregate metrics, and model metadata. They may not contain row identifiers or row-level values.

## Derived features

The challenger may add only these features, all computed from existing inputs:

- `CREDIT_INCOME_RATIO = AMT_CREDIT / AMT_INCOME_TOTAL`
- `ANNUITY_INCOME_RATIO = 12 * AMT_ANNUITY / AMT_INCOME_TOTAL`
- `GOODS_CREDIT_RATIO = AMT_GOODS_PRICE / AMT_CREDIT`
- `INCOME_PER_FAMILY_MEMBER = AMT_INCOME_TOTAL / CNT_FAM_MEMBERS`
- `EMPLOYED_AGE_RATIO = abs(DAYS_EMPLOYED) / abs(DAYS_BIRTH)`

Zero denominators must become missing values rather than infinity. Input frames must not be mutated.

## Challenger acceptance gates

The study is evidence, not an automatic deployment mechanism. Report all candidates and nominate a
candidate only when every applicable gate passes on development out-of-fold predictions:

- Calibration candidate:
  - Brier score improves by at least 0.0005 against its uncalibrated parent;
  - the upper bound of the paired 95% bootstrap interval for Brier delta is below zero;
  - log loss does not worsen;
  - AUC changes by no more than 0.001 in absolute value.
- Derived-feature candidate:
  - AUC improves by at least 0.003 against the current feature set;
  - the lower bound of the paired 95% bootstrap interval for AUC delta is above zero;
  - Brier score worsens by no more than 0.0002;
  - no existing public input is removed or redefined.

If no candidate passes, the report must say that the incumbent remains preferred. A rejected
challenger is a valid outcome and must not be massaged into a release claim.

## Monitoring reference and thresholds

Numeric reference distributions use ten development-sample quantile bins with `-inf` and `inf`
outer bounds. Duplicate quantiles are removed. Categorical distributions include explicit
`<MISSING>` and `<UNSEEN>` buckets. PSI calculations use epsilon `1e-6` before normalisation.

The demonstration uses these predeclared statuses:

| Signal | Amber | Red |
|---|---:|---:|
| Numeric/categorical feature PSI | `>= 0.10` | `>= 0.25` |
| Predicted-PD PSI | `>= 0.10` | `>= 0.25` |
| Absolute missing-rate movement | `>= 0.05` | `>= 0.10` |
| Unseen-category rate | `> 0.00` | `>= 0.01` |
| Absolute approval-rate movement | `>= 0.05` | `>= 0.10` |
| AUC decrease when outcomes exist | `>= 0.02` | `>= 0.05` |
| Brier increase when outcomes exist | `>= 0.005` | `>= 0.010` |

Red takes precedence over amber; otherwise status is green. These thresholds are demonstration
controls, not universal industry limits.

## Replay/stress batches

Use a deterministic 10,000-row replay window from the existing test fold. The remaining 51,503
test rows form the disjoint out-of-sample monitoring reference window:

- `baseline_replay`: values unchanged.
- `mild_shift`: multiply income by 0.90, credit by 1.05, and set occupation missing for a seeded
  additional 10% of rows.
- `severe_shift`: multiply income by 0.70, credit by 1.20, and set occupation missing for a seeded
  additional 25% of rows.

Retain the original outcomes solely to show how the frozen model behaves under a controlled
counterfactual stress. Reports must not call these outcomes newly observed or realised.

## Operational telemetry

Each HTTP request log record must be one JSON object with:

- `event="http_request"`
- `request_id` generated by the service
- HTTP method
- route path
- response status code
- elapsed milliseconds
- service version
- loaded model version when available

The record must not contain bodies, query strings, headers, decisions, reason codes, applicant
values, or IP addresses. Exceptions must still produce a timing/status record.

## Versioning

- Set the FastAPI service version to `1.3.0` because observability and health metadata change.
- Keep the fitted model version at `1.2.0` unless a later promotion plan replaces the artifact.
- `/health` must remain backward compatible by retaining `status` and `model_loaded`, while adding
  `service_version` and `model_version`.

## Release checks

The release is complete only when:

- all unit and integration tests pass;
- Ruff lint and formatting checks pass;
- the challenger and monitoring commands are deterministic across two runs;
- generated reports contain no absolute workstation paths or row-level applicant data;
- all three dependency files remain synchronised for shared runtime packages;
- both Docker images build;
- the standalone API container passes health and prediction smoke tests;
- the Streamlit dashboard still scores through the API and local fallback;
- the README and model card clearly label simulated monitoring and the unchanged v1.2 model;
- `git diff --check` reports no whitespace errors.
